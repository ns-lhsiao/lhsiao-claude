# Local devbox-ui Docker Stack

## webui local devbox-ui docker stack

- **The local webui dev environment is a self-contained docker stack started from the `devbox-ui` repo (`/Users/lhsiao/ns/git/devbox-ui`), NOT a connection to a remote tenant DB.** `docker compose up` brings up: a `web` container hosting the PHP BFF (CodeIgniter, php-fpm 8.1) live-mounted from `${NS_WEB_UI_DIR}/src/webui/system_framework → /var/www`, listening TLS on `:443` (host `developer.vbox`/`dev-developer.vbox` → 127.0.0.1); a local `mariadb` (host port 3309, root/1234); an `angular-ui` nginx on `:4200`; plus the `mf-*`/`ms-*` microfrontend/service sidecars. PHP connects to the LOCAL mariadb — the served tenant is whatever that DB holds (this box: `tenant13986db`, config_id=0). Login `developer@netskope.com` at `https://developer.vbox`, webui hash routing `/ns#/...`.
- **The served Angular is NOT `neo/dist`.** `neo/dist` is empty; `angular-ui` mounts it but the app actually loads from `system_framework/UI_Layer/dist/dev-lazy/` (built by `cd neo && npm run build:dev-lazy` → output `../system_framework/UI_Layer/dist/dev-lazy`, deploy-url `/UI_Layer/dist/dev-lazy/`), served by the `web` container off the system_framework mount. `/ns` index.html references `UI_Layer/dist/dev-lazy/main.<hash>.js`. `npm run dev:watch-lazy` (README step 13) is the watch variant; a one-shot `build:dev-lazy` also works.
- **`build:dev-lazy` OOMs V8 with default heap** — a backgrounded `nohup npm run build:dev-lazy` "exit 0"'d but produced NO output dir (silent crash: `FATAL ERROR: Reached heap limit`). Fix: `NODE_OPTIONS="--max-old-space-size=8192" npm run build:dev-lazy`. Build ~110s, main bundle ~14.8 MB.
- **A blank Angular shell (bodyLen 0, login form never renders) is usually a dev-lazy manifest⇄bundle desync, not an app bug.** `UI_Layer/dist/dev-lazy/angular_view.txt` is the bundle-ref manifest PHP serves into `/ns` index.html; an interrupted/OOM'd `build:dev-lazy` leaves it pointing at stale hashes (e.g. `main.aafd1da7...`) that are NOT on disk (disk has `main.443d7a90...`), so every bundle 404s and nothing mounts. Tell: `curl -sk https://<host>/ns | grep dist/dev-lazy` shows a `main.<hash>` that `ls dist/dev-lazy/` doesn't have. Fix: re-run `NODE_OPTIONS="--max-old-space-size=8192" npm run build:dev-lazy` to completion — it rewrites `angular_view.txt` and the bundles together in sync. Confirmed 2026-08-18 (ENG-1129819).
- **To serve a worktree's fix instead of the primary checkout**, repoint `NS_WEB_UI_DIR` and recreate the two file-mount containers: build dev-lazy in the worktree, then `cd devbox-ui && NS_WEB_UI_DIR=<worktree> docker compose up -d web angular-ui`. Both the PHP change (system_framework mount) and the Angular change (dev-lazy under it) swap together. Verify with `docker inspect web --format '{{range .Mounts}}...'` (source path) and `curl -sk https://developer.vbox/ns | grep dist/dev-lazy` (served bundle hash matches the worktree build). Confirmed 2026-08-03 (ENG-1149041).
- **Session backend is `memcached`, NOT the `tenant<id>db.ci_sessions` table** — that table exists but is unused on this stack; `sess_driver` resolves to memcached at runtime despite config.php's DB fallback branch. Cookie value is base64 `nsmemcached` + real id (decode the `bnNtZW1jYWNoZWQ...` prefix to confirm). Session key in memcached = `ci_session:<HTTP_HOST>:<session_id>` (`NS_Session_memcached_driver.php`). Inspect directly: `printf 'get <key>\r\n' | docker exec -i memcached nc -w2 localhost 11211` (raw get shows garbled output if the value is memcached-client-compressed — use PHP's own Memcached ext instead: `docker exec web php -r '$m=new Memcached();$m->addServer("memcached",11211); var_dump($m->get("<key>"));'` for a clean decompressed read). `mariadb` root creds for direct queries: `docker exec mariadb mariadb -uroot -p1234 -e "..."`.
- **Login on this devbox silently orphans the session — `session_regenerate_id()` migrates data to a new memcached key correctly but the response `Set-Cookie` never reflects the new id**, so the browser keeps resending the pre-login cookie forever and `login/isAccessAllowed` always reports `authenticated:false` even though server logs show "successfully logged in." Root: `NS_Session::isRegenerateNeeded()` (`application/libraries/Session/NS_Session.php`) fires `sess_regenerate()` on every `login/authenticate` (session-fixation hardening); on this stack the regenerated id's cookie update is lost (confirmed via raw CDP `Set-Cookie` capture — value never changes across the whole flow, including the authenticate POST response itself). No PHP error/warning surfaces (`error_reporting(E_ERROR|E_RECOVERABLE_ERROR)` globally excludes E_WARNING, and `session_regenerate_id()` failures are warnings). **Workaround (worktree-local only, NEVER commit)**: add an early `return false;` at the top of `isRegenerateNeeded()` with a `DEVBOX-TEMP` comment — disables regen-on-login so writes stay on one stable id (plain writes to a stable id already work fine). Must revert before finishing (`git checkout -- .../NS_Session.php`). Confirmed 2026-08-27/28 (ENG-868849 validation attempt).
- **Fast pre-check for a `$5$` (SHA-256 crypt) password before burning a full Playwright login attempt**: `openssl passwd -5 -salt <salt-from-stored-hash> '<candidate-password>'` and compare byte-for-byte against `admin_users.password`. Extract the salt as the 2nd `$`-delimited field. Saves a ~20min login-flow cycle when the password is simply wrong.
- **If the pre-check confirms the stored hash really doesn't match the documented credential, just overwrite it — this is a devbox-only test account, safe to reset.** Generate a new `$5$` hash with PHP's own `crypt()` (must match the algo id the app itself uses, not `openssl passwd -5`'s slightly different output format) from inside the `web` container: `docker exec web php -r '$salt="$5$".substr(md5(mt_rand()),0,16)."$"; echo crypt("<new-password>", $salt);'`, then `docker exec web mysql -h mariadb -u root -p1234 <tenant_db> -e "UPDATE admin_users SET password='<hash>', num_failed_login=0 WHERE username='<user>';"`. Clear `num_failed_login` in the same statement — a prior bad-password attempt increments it and can lock the account even after the hash is fixed. Confirmed 2026-08-28 (ENG-868849).
- **Raw `fetch()` to a PHP ajax endpoint (e.g. `/login/isAccessAllowed`) without `X-Requested-With: XMLHttpRequest` returns the SPA's `index.html` shell (200, `text/html`), not JSON** — CodeIgniter's `is_ajax_request()` check fails, routing `NS_Controller`'s non-ajax branches (e.g. `checkForValidSession()`) to a browser `redirect()` instead of an ajax JSON error. Always set that header when probing PHP ajax endpoints directly instead of through the Angular app's own HttpClient.
- **Waiting for `domcontentloaded` before `page.waitForSelector('#username')` on the login page can find ZERO inputs** — `/login` returns a JSON redirect (`{"redirect":"/ns#/login"}`) that the Angular SPA then has to boot and route through; `domcontentloaded` fires before Angular mounts the form. Use `page.goto(url, {waitUntil: 'networkidle'})` for the login page specifically.
- **CORRECTION 2026-08-28 — the "RBAC v3 role 1 has no permissions" conclusion below was WRONG; role 1 has full `rw` on `client_configuration`.** The earlier probe hit `http://localhost:3022/roles/1` bare and got a 500 "Unable to get version details" — that's `ms-rbac`'s version-middleware choking on a MISSING `x-netskope-tenantid` header, not a permissions verdict. The real call (matching what webui's PHP sends, see `Rbac_v3_service_config_model::getAdditionalHeaders()`) needs all four headers: `x-netskope-tenantid: <tenantid>`, `x-netskope-user-role-id: <roleId>`, `x-netskope-user-id: <email, NOT numeric id>`, `x-netskope-trid: <any string>`. With those, `curl localhost:3022/roles/1 -H ...` returns role 1 ("Tenant Admin") with `apiGroupId 26 client_configuration: rw` already present — RBAC data was never the blocker. `role_v3_permissions`/`role_v3_pages` tenant-DB tables are a red herring for this check; `hasPermission()`'s RBAC-v3 branch (`isRBACv3Enabled()` is hardcoded `true`) calls `rbac_v3_service_model->getPagePermission()` → `getAllPagePermissionsFromApi()` → this same `ms-rbac` HTTP call, not a local DB read. If a Settings page still denies access after confirming role permission this way, look elsewhere (session state, CSRF — see below), not at RBAC seed data.

- **The devbox `web` container's tenant-hostname lookup is an EXACT string match on `HTTP_HOST` including port** — `NS_Loader::getTenantDataByHost()` does `WHERE ui_hostname = $host` against `core_data.org_info` (`ui_hostname` is `UNIQUE`, stores literal `developer.vbox`, no port). Any per-slug port-offset scheme (`https://developer.vbox:8445`) makes `HTTP_HOST` become `developer.vbox:8445`, which matches NOTHING — tenant resolution fails ("Could not recognize the tenant") even though the container itself is healthy. This means the `boot-playwright`/`webui-angular-devbox` recipe's per-slug `web-<slug>` port-offset scheme (Step 4) is **incompatible with actually loading tenant data** — it only works for static asset serving. For anything that logs in or hits tenant-scoped PHP, repoint the SHARED `web`/`angular-ui` containers at the worktree instead (bare `:443`, `developer.vbox` with no port) and accept only one webui worktree being served at a time.
- **CSRF token used by a live Angular session is NOT the static `<meta name="ns-csrf-hash">` value baked into the initial page HTML — read it live.** `CsrfTokenStore` (`neo/src/app/common/services/security/csrf-token-store.service.ts`) reads the meta tag ONCE at bootstrap, but can refresh it later via `/login/getToken` (broadcast over a `BroadcastChannel`) — so the meta tag goes stale mid-session. Recomputing `token = btoa(csrfHash + location.host)` from the (stale) meta tag and POSTing it produces a "CSRF Token mismatch-CSRF attack suspected" 401 (`NS_Security::csrf_verify()`, `application/core/NS_Security.php:201`), which then cascades into subsequent 401s and an eventual silent redirect to `#/login?reason=loggedout` — this is what actually causes a Settings sub-page to look "permission denied" or "keeps bouncing to dashboard" when the real cause is a stale token, not RBAC. Fix: always pull the CURRENT token from the page's own JS state — `window.ns.getCsrfToken()` (exposed by the same service) — never recompute from the meta tag once the session has been alive a while.
- **Driving a PHP (CodeIgniter) endpoint end-to-end from Playwright: use in-page `fetch()`, not a cloned-cookie curl.** The auth cookie (`ci_session`) is `httpOnly` — `document.cookie` returns `""` for it; extract it with `playwright-cli state-save <file>` (or `context.storageState()`) if you truly need it outside the browser. But the simpler, more reliable pattern is to skip cookie-cloning into curl entirely and run the POST as an authenticated in-page fetch instead: `page.evaluate(async () => { const token = window.ns.getCsrfToken(); const body = new URLSearchParams({...fields, token}); return fetch('/settings/.../saveX', {method:'POST', credentials:'same-origin', headers:{'Content-Type':'application/x-www-form-urlencoded','X-Requested-With':'XMLHttpRequest'}, body: body.toString()}).then(r => r.text()); })` — this reuses the exact live session + live CSRF token with zero risk of cookie-encoding/header mismatches, and still lets you assert on the real HTTP response body. Confirmed end-to-end validating ENG-868849 (PR #18659) against `Clientconfiguration::saveClientConfig`, including a counterfactual (temporarily `git checkout <parent-branch> -- <model file>` to strip the fix, rerun the same fetch, confirm the bug reproduces, then `git checkout HEAD -- <file>` to restore).
- **Feature flags (`_isFeatureEnabled()`) read from `$_SESSION` userdata populated at login — there is no simple per-tenant DB row to flip.** Unlike control flags (which have the `control_<NAME>` cookie override under `HTTP_DEV_ENVIRONMENT`, see cert-rotation entry above), no such override exists for feature flags in this codebase. `core_data.global_flags` (name/value, no tenant scoping) and the hardcoded defaults array in `Admin_userdata_model::getFeaturesArray()` are both red herrings — neither is what `_isFeatureEnabled()` reads. Fastest reliable local override: a temporary `DEVBOX-TEMP`-tagged early-return in `_isFeatureEnabled()` itself (`application/helpers/show_feature_helper.php`) for the one flag name you need, mirroring the existing `isRegenerateNeeded() return false` pattern — revert before finishing.
- **UPDATE 2026-08-28 — `um-api-service-ext.qa01-mp-npe.nc1.iad0.nsscloud.net` unreachable from devbox was a DNS-scope issue, not a dead host.** The remote config (`/opt/ns/common/remote/um-api-service`, NOT `/opt/remote/...` — wrong path looks identical but returns "No such file" and is a red herring) already points at that host. It resolves fine from the Mac host via the VPN's macOS split-DNS supplemental resolver (`scutil --dns` → nameserver `172.18.16.147` for the `nsscloud.net` domain specifically), but the `web` container only sees Docker's embedded resolver (`127.0.0.11` → host's plain `/etc/resolv.conf`, which does NOT carry macOS's per-domain split-DNS routes) — so container DNS fails even though the host resolves it fine. Same root cause class as the other qa01-mp-npe hosts (`queryservice-int`, `api-gateway-controller-int`, etc.), which work ONLY because `devbox-ui/web/scripts/nswebui_start.sh` hardcodes them into `/etc/hosts` at container start — `um-api-service-ext` was simply missing from that list. Fix: resolve the IP once from the host (`nslookup <host> 172.18.16.147`) and add an `echo '<ip> um-api-service-ext.qa01-mp-npe.nc1.iad0.nsscloud.net' >> /etc/hosts` line to `nswebui_start.sh` alongside the existing entries, then recreate the web container. Confirmed 2026-08-28, ENG-868849 PR #18659 validation.
- **Live curl validation of `Steering_exception::deleteSelectedExceptions` (and likely other settings write endpoints) hit THREE independent, unrelated devbox issues stacked on top of each other** — don't assume fixing one means you're clear. (1) Role 1 (this devbox's seeded admin, `lhsiao@netskope.com`) gets a rich "Permission denied" (`current_page: Steering Configuration`) from `hasControllerPermissionV2()` even though a direct `curl localhost:3022/roles/1` AND the page→apiGroup mapping (`localhost:3022/apigroups/pageMapping`, page "Steering Configuration" → apiGroup "steering_configuration" id 20) both confirm role 1 has `rw` — the denial's root cause was never isolated (plausibly a session `roleId`/`tenantid` mismatch feeding `Rbac_v3_service_config_model::getAdditionalHeaders()`, or a stale cached permission result); a `DEVBOX-TEMP` early-`return true` in `hasControllerPermissionV2()` gated to the specific controller class is the fastest workaround, revert before finishing. (2) The authenticated session idles out surprisingly fast (tens of minutes of investigation in between = session timeout, `{"status":"timeout",...}`) — don't leave a long gap between login and the actual write call, or re-login immediately before it. (3) Re-login after a timeout can ALSO fail outright with a generic "backend error" — `docker logs web --tail 40` showed `CURL Error (6) Could not resolve host: ms-platform.ngweb` from `Rbac_v3_admins_model::fetchUserDetailsByUsername` (SAML-login user lookup), the same DNS-scoping bug class as the `um-api-service-ext` entry above (missing `/etc/hosts` line in `nswebui_start.sh` for `ms-platform.ngweb` specifically) — add it there rather than debug further per-attempt. Given this stacking, a single scriptable curl check for a settings write endpoint here is NOT a quick 5-minute validation; budget for it or fall back to PHPUnit + a note in the report that live validation was blocked by pre-existing devbox issues. - **`NS_WEB_UI_DIR=<empty string>` (e.g. `NS_WEB_UI_DIR= docker compose up ...`) does NOT fall back to any default** — `docker-compose.yml` has no `${NS_WEB_UI_DIR:-default}` syntax, it's a plain required substitution, so an explicitly-empty value resolves mount source paths to bare fragments like `/src/webui/...` (missing the repo root), and container creation fails: `unable to start container process ... mount src=/src/webui/webconfigs/php.ini ... not a directory`. To repoint back to the primary checkout, pass the actual absolute path (`NS_WEB_UI_DIR=/Users/lhsiao/ns/git/webui docker compose up -d --force-recreate web angular-ui`) — never just unset/empty it and hope for a default. Confirmed 2026-09-17 (ENG-1287334).
- **The CSRF-hash-rotation + session-instability stacking documented below (see the `Steering_exception::deleteSelectedExceptions` entry) is NOT specific to Steering Configuration** — it reproduced identically on `inline-policy-page` (RTP/CFW policy create form): every POST during the page's parallel initial-load XHRs failed `NS_Security::csrf_verify()` ("CSRF Token mismatch... UI-RESOURCE='inline-policy-page'") and force-logged-out the session, even after applying the `isRegenerateNeeded()` session-orphan workaround. When that workaround alone isn't enough, the next-level fix is a `DEVBOX-TEMP` early `return $this;` at the very top of `NS_Security::csrf_verify()` (`application/core/NS_Security.php`) — bypasses the check entirely for the local session, revert before finishing. Even with CSRF bypassed, a THIRD independent issue can still occur: an intermittent session-timeout eviction (`#/logout?reason=timeout`) on the same page load, distinct from both the regen bug and CSRF — retry once; if it doesn't reproduce on retry it's the parallel-XHR race, not a deterministic blocker. Budget for 2-3 stacked devbox issues on any POST-heavy page, not just Settings pages with many initial fetches. Confirmed 2026-09-17 (ENG-1287334).
- **`docker compose -f base.yml -f override.yml` concatenates `ports:` lists across files instead of replacing them** — an override setting `ports: ["8445:443"]` for a service whose base file already has `ports: ["443:443"]` (or `4200:80`) ends up with BOTH port mappings applied, and container creation fails with `Bind for :::4200 failed: port is already allocated` because the base port is still claimed by the original container. Fix (Compose v2.24+, confirmed working on v2.40.3): tag the override value `ports: !override ["8445:443"]` to fully replace rather than merge the list. Hit this bringing up a per-slug `web-<slug>`/`angular-ui-<slug>` pair per the `boot-playwright`/`webui-angular-devbox` recipe — the recipe's own override YAML omits `!override` and will collide with the base stack's already-running default `web`/`angular-ui` containers.
