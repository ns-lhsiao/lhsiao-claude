# Infra: Nginx, K8s, GitHub Actions

## ngweb_mf / Nginx

- **`ngweb_mf` upstream returns 401 (NOT 404) for missing `x-npe-env` builds**. The `@mf_npe_fallback` only fires on `error_page 404`, so env-prefixed paths are served as final 401 (auth-off paths) or rewritten to the 174 KB static `/error_pages/404.html` (via `error_page 401 =404`). `/npe-ngssl-check` Mode A/B audits only check static wiring — pair with a live curl to `/mf/<app>/build-info.json` (auth-off) comparing no-header vs `x-npe-env: npe-anything`. Real fix: widen `error_page 401 404 = @mf_npe_fallback` gated by `$http_x_npe_env`, or fix the upstream to return 404.
- **`auth_request` failures masquerade as 404** via chained `error_page`. An unauth'd curl to `/mf/<app>/remoteEntry.js` returns 404 with a 174 KB HTML body — that's `auth_request` 401 rewritten by `error_page 401 =404 /error_pages/404.html`. To isolate auth from upstream behavior, probe `/mf/<app>/build-info.json` (`auth_request off`). Tell: a 404 with multi-hundred-KB HTML; real upstream 404s are short.
- **A `/api/v2/...` 404 whose body is the 21-byte plain-text `default backend - 404` (`content-type: text/plain`, `server: nginx`) is the ingress-nginx DEFAULT BACKEND — it means NO ingress rule matches that path in that cluster, i.e. the upstream microservice is not deployed in that DC. It is NOT an application 404 and NOT an api-gateway route-missing.** Application-level 404s from the tenant edge return JSON (e.g. featureflags → `{"message":"Flag not found","error":"Not Found","statusCode":404}`). Diagnostic drill for "feature X not loading only in env Y": in the HAR, list every `/api/v2/*` entry with `status | server | content-type`, then check whether a SIBLING path under the same prefix succeeds — e.g. `/api/v2/platform/admin/preferences` 200 JSON while `/api/v2/platform/dnsresolver/*` 404 text/plain proves the `/api/v2/platform/` prefix routes fine and only that one service has no live upstream. Scoping the failure to a single service family this way turns a "frontend bug" into a deployment ticket in one step; do this BEFORE pickaxing frontend code. Also confirm the gateway spec is not the gap by grepping `api-gateway-endpoints` for the path (`{non,}production/endpoints/<domain>/<svc>.yaml`, `x-netskope-params.serviceConfig` names the upstream) — spec present + `enabledInProduction: true` on both sides means the contract shipped and only the rollout is missing. Confirmed 2026-08-19 (ENG-1185033: mf-cfw DNS Resolver blank on stg01, upstream `polaris-dnsaas-gw-tenant-api` undeployed in STG-IAD0, tracked by SNA-38808).
- **A missing-upstream env gap surfaces as a blank UI (not an error) whenever the frontend never reads the error channel — so "not loading" tickets land on the frontend team by default.** mf-cfw DNS Resolver: `DNSResolverHome.tsx` did `fetchDNSServerIp().then(...)` with no `.catch()` (rejection → store default `''` → blank label), and `DNSResolverTable.tsx` destructured only `{isLoading, data}` from the react-query hook, never `isError`, so a 404 rendered the "No source IP location created" empty state — indistinguishable from a genuinely empty list. When triaging "X is not loading", check the error channel is actually consumed before accepting the symptom framing; the silent-failure debt is usually a separate, older ticket than the env gap that exposed it.

## Ops: K8s, Helm, Slack, Bash

- **`helm list -n ngweb-v2` misses YAP-deployed sidecars**. Ground truth is `kubectl get deploy -n ngweb-v2`. Filter by Deployment-name convention `<service>(-npe-<suffix>)?`. The `app.kubernetes.io/instance` label only works for helm-deployed sidecars.
- **No NGWeb GH Actions workflow helm-deploys directly from the runner — every deploy routes through an in-cluster pipeline; the runner has no kubeconfig.** Correcting a wrong assumption (2026-08-21, client-oppy sidecar design): I proposed `helm upgrade --install` from a GH runner for a client-oppy PR sidecar. Not feasible. Two mechanisms exist, neither runner-side: (1) **ngweb-v2/YAP world** (Node MF services) — CI packages chart + registers a Hubble manifest, then triggers the YAP pipeline (Rancher token) which deploys in-cluster; see `ngweb-actions/.github/workflows/on-demand-sidecar-deploy.yml`. (2) **client-oppy (Go services)** — the nightly calls `netSkope/cd-deployment-workflow/.github/workflows/deployment.yaml`, which merely runs a docker `cd-jenkins-wrapper` that triggers Jenkins job `one_button_client-oppy_helm` with a `jenkinsTriggerParameterJson`; **Jenkins** runs helm inside the cluster. client-oppy repo has ZERO cluster secrets. The one_button param `COMPONENT_NAME` names the release AND selects the Artifactory chart (`HELM_CHART_PATH: "COMPONENT_NAME"`), so a sidecar (distinct release name, same chart, extra values overlay) is NOT expressible in the current job — it needs a Jenkins-job change (CD/PE team owns `one_button_client-oppy_helm`) or a per-PR uniquely-named chart. Verify the deploy path (grep for `kubeconfig`/`RANCHER`/`JENKINS` secrets + the reusable-workflow the caller invokes) BEFORE designing any sidecar/deploy automation.
- **Webui MP-Prod namespace**: `<dc>-mp-prod--webui` (e.g., `dfw3-mp-prod--webui`). The `c4-<dc>` style is AM2-specific or outdated. Confirm with the engineer before writing namespace names into a CM.
- **Slack `section.text` with `\n` separators can collapse into one line** (client-dependent). For lists, emit one `section` block per row (optionally with `divider` blocks). Also a prerequisite for per-row `accessory` buttons.
- **Multi-line jq in shell needs trailing `\` on the closing-quote line**. Bash tolerates raw newlines INSIDE `'…'`, but once the closing `'` appears, a bare `|` on the next line is a syntax error. Fix: `] | @tsv' \` then `| sort)`. Validate with `bash -n` on the `run:` block before pushing YAML.

## GitHub Actions: which workflow version + token identity

- **`pull_request` runs the HEAD/merge version of the workflow YAML, not the base branch.** Correcting an earlier wrong assumption: only `pull_request_target` (and `push` to a branch) uses the base/target-branch copy. For `pull_request` on a same-repo branch, the workflow file executed is the PR head merged into base, WITH secrets and a read/write token. Fork PRs run the head version too but get a read-only token and NO secrets. Practical upshot: you can e2e-test a workflow-file change WITHOUT merging to the trigger branch — cherry-pick the change onto a same-repo PR branch and push; the modified YAML runs. Verify via the run's `head_sha`/`path` (`gh api /repos/O/R/actions/runs/<id> --jq '{path,head_sha}'`). Confirmed 2026-08-21 (webui2 balkan-pr-scope: cherry-picked the PAT fix onto demo branches, scope run head_sha = the cherry-pick commit, fixed step ran).
- **A label added with the default `GITHUB_TOKEN` (`github.token`) does NOT trigger another workflow.** GitHub's recursion guard suppresses workflow triggers from events created by `GITHUB_TOKEN` (exceptions: `workflow_dispatch`, `repository_dispatch`). So `gh pr edit --add-label` under `GH_TOKEN: ${{ github.token }}` fires a `labeled` event on the timeline but no `on: pull_request: types: [labeled]` workflow picks it up. Fix: stamp with a PAT or GitHub App token (a distinct identity) — then the `labeled` event fires normally. webui2 balkan-pr-scope → pr-sidecar used `EP_FALCON_PT_TOKEN_DEFAULT`. Symptom before fix: label present on PR but zero `labeled`-event runs; only the `opened` run exists (parked `waiting`). Confirmed 2026-08-21 (PR #2278, demo #2271).

## GitHub Actions: local action refs in reusable workflows

- **Step-level `uses: ./.github/actions/<x>` inside a REUSABLE workflow resolves to the CALLER's `$GITHUB_WORKSPACE`, not the reusable workflow's own repo.** Failure: `Can't find 'action.yml' ... under /home/runner/_work/<caller>/<caller>/.github/actions/<x>`. This differs from JOB-level `uses: ./.github/workflows/<x>.yaml` (calling another reusable workflow), which DOES resolve to the repo+ref of the workflow declaring the job. So composite/local actions invoked from a reusable workflow's steps MUST use an absolute `owner/repo/path@ref`. There is no built-in "same ref as this workflow" for `uses:` — hardcoding `@develop` is the common practice; to test a feature branch's action changes end-to-end, temporarily pin the absolute ref to the PR branch and revert to `@develop` before merge. Repro: ngweb-actions service_cicd.yaml manifest-and-deploy (ENG-1052961).
