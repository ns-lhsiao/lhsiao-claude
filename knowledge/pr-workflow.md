# PR & GitHub Workflow

## PR & GitHub Workflow

- **Check PR state before pushing follow-up commits**. `gh pr view <num> --json state` — if MERGED, the commit becomes orphaned. Also when the user starts a squash-merge mid-edit, anything pushed between "merge clicked" and "squash completed" gets dropped. Confirm via `gh api repos/OWNER/REPO/compare/main...<branch>` — "behind by N, ahead by 0" = already merged. Failure: scheduled workflow still has the bug you "just fixed."
- **Transferred-repo origin URL lies**: a fork transferred to upstream still shows the old URL but pushes land upstream. Confirm with `gh pr view <num> --json headRepositoryOwner,headRepository`. Stop the redirect notice via `git remote set-url origin git@github.com:netSkope/<repo>.git`.
- **A repo's `commitlint.config.js` can override the global Conventional-Commits header format.** mf-cfw runs `commitlint-plugin-jira-rules` (`extends: ['jira']`) via a husky `commit-msg` hook, which requires the header to start with `<JIRA-KEY>: <subject>` (e.g. `ENG-1266588: Add ...`) — a `feat: ...` Conventional-Commits header (per the global CLAUDE.md default) fails with `jira-task-id-project-key`/`jira-task-id-case` errors and the commit never lands (no partial commit, safe to just retry). Before committing in an unfamiliar repo, check for `commitlint.config.js` / `.commitlintrc*` and match its expected header, keeping the global convention only for the body prose. Confirmed 2026-09-15 (ENG-1266588, mf-cfw).
- **`gh pr edit` needs `read:project` scope**. Use REST instead: `gh api repos/OWNER/REPO/pulls/N -X PATCH -f body="..."`. The `-X PATCH` is required. For a large/multiline body, pass it as a file: `gh api --method PATCH repos/OWNER/REPO/pulls/N -F "body=@/path/to/body.md"` (`-F key=@file` sends the file *contents* as the string value; `-f`/`-F` inline args mangle newlines).
- **Embedding screenshots in a PR on a PRIVATE repo**: `raw.githubusercontent.com` URLs 404 without auth and GitHub's camo image proxy can't fetch them, so pushing shots to a fork branch and referencing raw URLs does NOT render. The only host that renders for collaborators is GitHub **user-attachments** (`https://github.com/user-attachments/assets/<uuid>`), and there is **no public REST/GraphQL API** to mint one — upload requires a logged-in web session (drag-drop, or Playwright automation, see playwright.md). External public hosts (imgur/S3) render for everyone but leak internal tenant data — avoid for QA shots. Confirmed 2026-08-26 (ENG-1152682, mf-client #1250).
- **Two DIFFERENT signed-token systems exist for `raw.githubusercontent.com` on a non-public repo — don't confuse them.** Bare raw URLs always 404 on anything not fully public (`private:true` repos, including GH Enterprise `visibility:internal`, need auth). Two ways to get a working token, with very different lifetimes — tell them apart by prefix:
  - **`?token=GHSAT0...`** — minted by GitHub's own web UI when a logged-in user clicks the blob page's "raw" button / copies the link. Long-lived, ~7 days per GitHub docs; confirmed still 200 a month later in practice. Not obtainable via REST API — requires an authenticated browser session (see the GitHub-SSO persistent-profile pattern in playwright.md).
  - **`?token=BRPETO...`** — minted by the Contents API's `download_url` field (`gh api "repos/O/R/contents/<path>?ref=<branch>" --jq '.download_url'`). Short-lived (confirmed dead within ~15–20 min, with NO re-fetch in between — this is a real TTL, not "invalidated by a second call" as I first assumed and wrongly noted here before correcting it). **Do not use this for anything that needs to render later than immediately** — it will look fine when you post it and be a broken image by the time a reviewer opens the PR.
  For a PR comment that needs to stay renderable, neither token is reliable long-term — get the repo owner to flip it fully public, or use the GHSAT0 (web-session) route if it must stay non-public. Confirmed 2026-08-28 (ENG-868849, webui #18660) — cost ~30 min of back-and-forth misdiagnosing this before finding the prefix distinction.
  - **Getting a GHSAT0 token headlessly (no manual browser)**: reuse the persistent GitHub profile from playwright.md's SAML pattern (`chromium.launchPersistentContext('/tmp/gh-pw-profile', {channel:'chrome', headless:true})`); if already SSO'd, cookies just work. If not, one headed pass (`headless:false`) hitting any blob URL under the target repo is enough — Playwright auto-follows the Okta SAML redirect chain (`sso.netskope.io/.../saml` → `github.com/orgs/netSkope/saml/consume` → back to the target) with **zero manual interaction** as long as the underlying `sso.netskope.io` session cookie is already valid; poll `page.title()` until it stops saying "Sign in" / "Netskope - Sign In". Once authenticated, don't scrape the blob page's rendered `<img src>` (that's a `github.com/.../blob/...?raw=true` URL, doesn't carry the token) — instead `page.goto()` that same `?raw=true` URL directly and read `page.url()` after the navigation completes; GitHub 302s it through to the real `raw.githubusercontent.com/.../refs/heads/<branch>/<path>?token=GHSAT0...` and Playwright's `page.url()` reflects the final resolved address.
- **`gh api ... -f field=@/path/to/file` does NOT read the file — it sends the literal string `"@/path/to/file"` as the value.** This isn't `gh pr edit`-specific (see the pulls-PATCH note above) — it hit the same way on `PATCH /repos/O/R/issues/comments/<id>` with `-f body=@file.md`. Only `-F field=@file` (uppercase) reads from disk; `-f` is always a literal. Safer than remembering which flag: read the file into a shell var first (`BODY=$(cat file.md)`) and pass `-f body="$BODY"` — works either way and avoids the case-sensitivity trap entirely.
- **Changing a repo's visibility needs org-admin, not just push/write access** — `gh api -X PATCH repos/O/R -f private=false` as a regular contributor returns `422 "Visibility can't be changed by this user"` even though the same token can push commits and patch PR/issue content fine. Ask the repo/org owner to do it via Settings → General → Danger Zone.
- **Minting user-attachments URLs headlessly**: drive a Playwright persistent-profile browser to the PR, `setInputFiles` on the comment box's hidden file input (`#fc-new_comment_field`; the PR-body editor's is `#fc-<textarea-id>`, textarea `name="pull_request[body]"`). GitHub uploads on the `change` event and inserts an **`<img src="https://github.com/user-attachments/assets/<uuid>" …/>` HTML tag** (not markdown `![]()`) into the textarea — regex the `src`, don't submit the comment, then PATCH the real body via REST with your own captions. Input has `multiple`. Confirmed 2026-08-26 (ENG-1152682).
- **Moving a branch across remotes** can't retarget an open PR. Workflow: `gh pr close <num>` → `git push origin <branch>` → `gh pr create --head <branch>`. Delete the old-remote branch.
- **mf-client PR template**: H2 sections with emoji prefixes — `## 🎯 Jira Issue`, `## 📝 Description`, `## 🚧 Type of Change`, `## ✅ Checklist`, `## 🖼️ Screenshots`, `## 📌 Additional Notes`. Mirror `.github/pull_request_template.md` exactly.
- **webui PR template**: H4 sections (NOT H2) — `#### 🎯 Jira Issue`, `#### 📝 Change Description`, `#### 🚧 Type of Change`, `#### ✅ Checklist`, `#### 🧪 Manual Testing Done`, `#### 🖼️ Screenshots/Videos`, `#### 📌 Additional Notes`.
- **`netSkope/pr-screenshots` `develop` moves between sessions; a plain `git push` after committing can be rejected non-fast-forward.** Always `git pull --rebase origin develop` before `git push origin develop` in that repo (no PR flow, direct push). Hit 2026-09-03 (webui2 ENG-1252057).
- **`gh pr edit <n> --body-file` fails with `your authentication token is missing required scopes [read:project]`** because `pr edit` pre-fetches project boards even when only editing the body. Do not `gh auth refresh` for it; use the REST API directly: `gh api -X PATCH repos/<org>/<repo>/pulls/<n> -F body=@/path/body.md`. `gh pr create` and `gh pr view` are unaffected. Hit 2026-09-03 (webui2 #2500).
- **`gh search code` / `gh api search/code` can return 0 results for a string that verifiably exists in the file** — confirmed by independently fetching the file and grepping it directly. GitHub's code-search index lags/misses on some private-repo content; a 0-result code search is NOT proof of absence. When a search result contradicts other evidence (git blame, a diff you already have), re-verify via direct file fetch instead of trusting the search. Hit 2026-09-13 (netSkope/service, ENG-1074579 follow-up) — `gh search code "nplan4571_datamigrate" --repo netSkope/service` returned nothing while the literal string was directly visible in the file moments later via raw fetch.
- **GitHub Contents API 404s on large files** (`gh api repos/O/R/contents/<path> -f ref=<branch>`) — hit this on a ~10k-line Python file well under any obvious size limit's expectation but apparently still over the Contents API's ceiling (~1MB base64-encoded). Fix: fetch via `curl -s -H "Authorization: token $(gh auth token)" "https://raw.githubusercontent.com/<org>/<repo>/<branch>/<path>"` instead — works for private repos with the `gh` token as a bearer `Authorization: token` header (no signed `?token=` query param needed, unlike the screenshot-embedding case earlier in this file — that's for anonymous/browser access, this is for authenticated API-style fetches and has no TTL issue).

## `gh` CLI fails inside the Bash sandbox (2026-09-16)
- `gh pr view/diff/api` in sandbox mode fails twice over: first
  `deny network-outbound api.github.com:443` (host not in `allowed_domains`), then — after adding
  `allowed_domains: ["api.github.com", ...]` — `tls: failed to verify certificate: x509: OSStatus -26276`,
  because the sandbox's filtering proxy MITMs TLS and `gh`'s Go TLS stack doesn't trust its CA.
- Fix: run every `gh` command with `dangerouslyDisableSandbox: true`. Adding the host to
  `allowed_domains` alone is NOT enough.
- Second trap: `$TMPDIR` differs between sandboxed and unsandboxed commands, so a file written by an
  unsandboxed `gh ... > $TMPDIR/x` is invisible to a later sandboxed `cd $TMPDIR`. Write to the
  session scratchpad path literally instead of `$TMPDIR` when mixing the two modes.
- Third trap: `gh api "…/contents/path?ref=pr/ENG-123/foo"` — zsh globs the bare URL and errors
  `no matches found`. Quote the whole argument or build it from a variable.

## `gh pr edit` fails with "missing required scopes [read:project]" (2026-09-23)
- `gh pr edit <n> --body-file f` errored: `your authentication token is missing required scopes
  [read:project]` — gh's edit path queries projectsV2 even when only the body changes.
- Fix without re-auth: `gh api -X PATCH repos/<org>/<repo>/pulls/<n> -F "body=@f"`.
- **Use `-F`, never `-f`, for the `@file` form (2026-09-24).** `-f body=@-` silently set the PR body to
  the literal two-character string `@-` and still returned 200 + the `html_url`, so it looks like it
  worked — only `gh api .../pulls/<n> --jq '.body | length'` (returned `2`) exposed it. `-f` is a plain
  string field with no `@` expansion; `-F` is the typed field that reads `@file` / `@-` (stdin).
  Most robust for multi-KB markdown bodies: build `{"body": "..."}` with `python3 -c "import json,…"`
  and pass `--input <file>`, then always verify with `--jq '.body | length'` before moving on.
