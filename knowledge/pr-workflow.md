# PR & GitHub Workflow

## PR & GitHub Workflow

- **Check PR state before pushing follow-up commits**. `gh pr view <num> --json state` — if MERGED, the commit becomes orphaned. Also when the user starts a squash-merge mid-edit, anything pushed between "merge clicked" and "squash completed" gets dropped. Confirm via `gh api repos/OWNER/REPO/compare/main...<branch>` — "behind by N, ahead by 0" = already merged. Failure: scheduled workflow still has the bug you "just fixed."
- **Transferred-repo origin URL lies**: a fork transferred to upstream still shows the old URL but pushes land upstream. Confirm with `gh pr view <num> --json headRepositoryOwner,headRepository`. Stop the redirect notice via `git remote set-url origin git@github.com:netSkope/<repo>.git`.
- **`gh pr edit` needs `read:project` scope**. Use REST instead: `gh api repos/OWNER/REPO/pulls/N -X PATCH -f body="..."`. The `-X PATCH` is required. For a large/multiline body, pass it as a file: `gh api --method PATCH repos/OWNER/REPO/pulls/N -F "body=@/path/to/body.md"` (`-F key=@file` sends the file *contents* as the string value; `-f`/`-F` inline args mangle newlines).
- **Embedding screenshots in a PR on a PRIVATE repo**: `raw.githubusercontent.com` URLs 404 without auth and GitHub's camo image proxy can't fetch them, so pushing shots to a fork branch and referencing raw URLs does NOT render. The only host that renders for collaborators is GitHub **user-attachments** (`https://github.com/user-attachments/assets/<uuid>`), and there is **no public REST/GraphQL API** to mint one — upload requires a logged-in web session (drag-drop, or Playwright automation, see playwright.md). External public hosts (imgur/S3) render for everyone but leak internal tenant data — avoid for QA shots. Confirmed 2026-08-26 (ENG-1152682, mf-client #1250).
- **Two DIFFERENT signed-token systems exist for `raw.githubusercontent.com` on a non-public repo — don't confuse them.** Bare raw URLs always 404 on anything not fully public (`private:true` repos, including GH Enterprise `visibility:internal`, need auth). Two ways to get a working token, with very different lifetimes — tell them apart by prefix:
  - **`?token=GHSAT0...`** — minted by GitHub's own web UI when a logged-in user clicks the blob page's "raw" button / copies the link. Long-lived, ~7 days per GitHub docs; confirmed still 200 a month later in practice. Not obtainable via REST API — requires an authenticated browser session (see the GitHub-SSO persistent-profile pattern in playwright.md).
  - **`?token=BRPETO...`** — minted by the Contents API's `download_url` field (`gh api "repos/O/R/contents/<path>?ref=<branch>" --jq '.download_url'`). Short-lived (confirmed dead within ~15–20 min, with NO re-fetch in between — this is a real TTL, not "invalidated by a second call" as I first assumed and wrongly noted here before correcting it). **Do not use this for anything that needs to render later than immediately** — it will look fine when you post it and be a broken image by the time a reviewer opens the PR.
  For a PR comment that needs to stay renderable, neither token is reliable long-term — get the repo owner to flip it fully public, or use the GHSAT0 (web-session) route if it must stay non-public. Confirmed 2026-08-28 (ENG-868849, webui #18660) — cost ~30 min of back-and-forth misdiagnosing this before finding the prefix distinction.
- **`gh api ... -f field=@/path/to/file` does NOT read the file — it sends the literal string `"@/path/to/file"` as the value.** This isn't `gh pr edit`-specific (see the pulls-PATCH note above) — it hit the same way on `PATCH /repos/O/R/issues/comments/<id>` with `-f body=@file.md`. Only `-F field=@file` (uppercase) reads from disk; `-f` is always a literal. Safer than remembering which flag: read the file into a shell var first (`BODY=$(cat file.md)`) and pass `-f body="$BODY"` — works either way and avoids the case-sensitivity trap entirely.
- **Changing a repo's visibility needs org-admin, not just push/write access** — `gh api -X PATCH repos/O/R -f private=false` as a regular contributor returns `422 "Visibility can't be changed by this user"` even though the same token can push commits and patch PR/issue content fine. Ask the repo/org owner to do it via Settings → General → Danger Zone.
- **Minting user-attachments URLs headlessly**: drive a Playwright persistent-profile browser to the PR, `setInputFiles` on the comment box's hidden file input (`#fc-new_comment_field`; the PR-body editor's is `#fc-<textarea-id>`, textarea `name="pull_request[body]"`). GitHub uploads on the `change` event and inserts an **`<img src="https://github.com/user-attachments/assets/<uuid>" …/>` HTML tag** (not markdown `![]()`) into the textarea — regex the `src`, don't submit the comment, then PATCH the real body via REST with your own captions. Input has `multiple`. Confirmed 2026-08-26 (ENG-1152682).
- **Moving a branch across remotes** can't retarget an open PR. Workflow: `gh pr close <num>` → `git push origin <branch>` → `gh pr create --head <branch>`. Delete the old-remote branch.
- **mf-client PR template**: H2 sections with emoji prefixes — `## 🎯 Jira Issue`, `## 📝 Description`, `## 🚧 Type of Change`, `## ✅ Checklist`, `## 🖼️ Screenshots`, `## 📌 Additional Notes`. Mirror `.github/pull_request_template.md` exactly.
- **webui PR template**: H4 sections (NOT H2) — `#### 🎯 Jira Issue`, `#### 📝 Change Description`, `#### 🚧 Type of Change`, `#### ✅ Checklist`, `#### 🧪 Manual Testing Done`, `#### 🖼️ Screenshots/Videos`, `#### 📌 Additional Notes`.
