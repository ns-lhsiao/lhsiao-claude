# QA01 Parallel Namespace Tenant Routing (rtp-XX)

By default every QA01 tenant hostname is served by one nginx config and lands in
the regular namespace `qa01-mp-npe--webui`. To test a feature branch you bind
specific tenant hostnames to a parallel namespace, so only those tenants reach
`qa01-mp-npe-rtpXX--webui`.

The binding is a `server_name` list in a per-namespace nginx server block on the
QA01 nginx VM, generated by `/etc/nginx/conf.d/pns_setup.sh`. Deploying the
namespace is a separate job -> `qa01-parallel-namespace-deploy`.

```
tenant hostname ──> ngsslwebui01 (shared VM, ALL qa01 tenants)
                      /etc/nginx/conf.d/webui_proxy_rtpXX.nginx.conf
                        server_name <your tenants>;
                          ├─ crane_tenant=0 -> host: webui-rtpXX  -> KLBI routes to the namespace
                          └─ crane_tenant=1 -> API Gateway + X-Netskope-Apigw-Upstream-Webui-Target
```

## Hard rules

- **This VM serves every QA01 tenant.** A bad config here breaks QA01 for
  everyone, not just your namespace. There is no staging copy and changes are
  live on reload.

- **`sudo nginx -t -c /etc/nginx/nginx-sslwebui.conf` before every reload, with
  no exceptions.** Note the explicit `-c`: the sslwebui config is not the
  default one, so a bare `nginx -t` validates the wrong file and tells you
  nothing. Never signal a reload on an unvalidated config.

- **`AskUserQuestion` is mandatory before the reload, and again before any hand
  edit of a config file.** Show the file, the current `server_name`, the intended
  `server_name`, and the `nginx -t` output. Re-confirm even if the user already
  approved earlier in the session -- the namespace or tenant may have changed.

- **Back up before any hand edit.** Removal has no tooling (see below), so it is
  a manual edit of a live root-owned config. Copy the file first; that backup is
  the rollback path.

- **Read `--help` from the copy on the VM, not from the runbook.** The deployed
  script has been observed to be newer than the published runbook -- it generates
  more files and supports capabilities the runbook does not document. Trust the VM.

- **Never point this at production.** The same `ngsslwebui0N` hostname pattern
  exists in every POP. Only `ngsslwebui01.qa01-mp-npe.nc1.iad0.nsscloud.net`
  (teleport cluster `iad0`) is in scope. Do not adapt these commands to a
  `*-mp-prod` host. The script enforces this structurally and refuses to run
  against a host that is not the QA01 NPE VM.

- **No audit log here, by design.** `pns_routing.py` performs no mutations at
  all -- `add` and `remove` emit a command sequence for a human to run -- so
  there is no write for this skill to record. The audit trail is the timestamped
  backup file left next to the config, plus the VM's own shell history. Contrast
  `qa01-parallel-namespace-deploy`, which does trigger and therefore does log.

This skill functions on a machine with no other Claude skill installed.
`confluence-reader` and `sumo-query` make some steps nicer and are referenced
where useful, but nothing here depends on them.

## Reaching the VM

Login first if no profile, or if it is expired:

```bash
tsh login --proxy=teleport.netskope.io
tsh status     # confirm a qa01-mp-npe role is present and the cert is valid
```

```bash
tsh ssh --cluster iad0 ngsslwebui01.qa01-mp-npe.nc1.iad0.nsscloud.net
```

**`tsh ls` will not help you find this host.** Node listing on this cluster
returns hundreds of `kaas-node-*` entries and no `ngsslwebui`; every
`tsh ls --search=ngsslwebui` / `--search=sslwebui` variant comes back empty, and
`tsh ssh` without `--cluster iad0` reports the host as "offline or does not
exist". The hostname and the cluster must both be supplied explicitly. Details
and the equivalent patterns for other POPs are in
`references/teleport-access.md`.

## Inspect (safe, do this first)

```bash
python3 scripts/pns_routing.py show               # every rtp namespace binding
python3 scripts/pns_routing.py show --ns-id rtp12 # one
```

By hand:

```bash
tsh ssh --cluster iad0 ngsslwebui01.qa01-mp-npe.nc1.iad0.nsscloud.net -- \
  'sudo grep -nE "^[[:space:]]*server_name[[:space:]]" /etc/nginx/conf.d/webui_proxy_rtp12.nginx.conf'
```

Two things that trip people up:

- The configs are `0600 root`, so plain `cat` gives `Permission denied`. Use `sudo`.
- **Anchor the pattern.** A loose `grep server_name` also matches
  `proxy_ssl_server_name on;` several times in the same file, so you get three
  hits and pick the wrong line. Only the anchored `^\s*server_name\s` match is
  the tenant list.

## Add a tenant

`pns_setup.sh` appends when a config for that `--ns-id` already exists, so the
same command creates a first-time setup or adds to an existing one. Existing
tenants are preserved.

```bash
python3 scripts/pns_routing.py add --ns-id rtp12 \
  --tenants myfeature-qa01.qa.boomskope.com --emit
```

`--emit` prints the exact commands and runs nothing. The commands are:

```bash
sudo bash /etc/nginx/conf.d/pns_setup.sh \
  --ns-id rtp12 \
  --webui-address webui-rtp12.qa01-mp-npe-rtp12--webui \
  --tenants myfeature-qa01.qa.boomskope.com

sudo nginx -t -c /etc/nginx/nginx-sslwebui.conf   # dry run - must pass first
# AskUserQuestion gate here
sudo supervisorctl signal HUP nginx               # prints: nginx: signalled
```

Notes:

- `--webui-address` is `webui-rtp<NN>.qa01-mp-npe-rtp<NN>--webui`; the script
  derives the KLBI host header from the part before the first `.`.
- Add `--apiv1-address webui-api-v1-rtp<NN>.qa01-mp-npe-rtp<NN>--webui` only if
  you need `/api/v1/*` routed too. On an append this is not re-read; it only
  takes effect at first-time generation.
- On a **first-time** setup the script refuses to overwrite existing generated
  files. Delete them first if you truly need to regenerate.
- Tenant values may be nginx regex patterns, e.g. `--tenants '~(a|b)\.example\.com$'`.
  Quote them so the shell does not expand them.
- **Cutover (crane) tenants** must already be listed in
  `/etc/nginx/crane_tenants.map`; that is what makes `$crane_tenant=1` and sends
  the request down the API Gateway path. See `references/nginx-internals.md`.

Expected output ends with a summary listing the merged tenant set -- confirm your
tenant is in it *and* that the pre-existing ones are still there.

## Remove a tenant

**`pns_setup.sh` cannot remove anything.** Its only flags are `--ns-id`,
`--webui-address`, `--apiv1-address`, `--tenants`, `--source`, `--out-dir`,
`--help`; when a config exists it appends and nothing more. So removal is a hand
edit of a live root-owned config -- the highest-risk operation in this skill.

```bash
python3 scripts/pns_routing.py remove --ns-id rtp12 \
  --tenants myfeature-qa01.qa.boomskope.com --emit
```

This reads the current `server_name`, computes the remaining set, and emits a
backup + edit + validate + reload sequence for a human to run. It never edits
anything itself.

Two cases:

- **Some tenants remain** -> rewrite the `server_name` line with the survivors.
- **No tenants remain** -> do not leave an empty `server_name`; tear the whole
  namespace config down instead (next section). An empty `server_name` is not a
  valid way to disable the block.

The emitted sequence keeps a timestamped backup next to the file. If `nginx -t`
fails, restore from that backup and re-validate *before* doing anything else --
never leave the VM with a config that fails validation, because the next reload
by anyone else will then fail too.

> Honest status: the add, validate and reload paths in this skill have been
> exercised end to end on rtp12. The removal path has **not** been executed
> against this VM; it is derived from the file layout and the script's confirmed
> lack of a remove flag. Treat the emitted commands as a reviewed proposal, read
> them before running, and keep the backup.

## Tear down a namespace's routing

When the namespace is finished with, remove its nginx footprint so the tenants
fall back to the regular namespace:

```bash
sudo rm /etc/nginx/conf.d/webui_proxy_rtp12.nginx.conf
sudo rm -rf /etc/nginx/conf.d/pns_rtp12

sudo nginx -t -c /etc/nginx/nginx-sslwebui.conf
sudo supervisorctl signal HUP nginx
```

The published runbook lists the generated files individually, but the deployed
script produces more than the runbook documents, so removing the whole
`pns_rtp<NN>/` directory is the reliable form. `rm -rf` on a path built from an
`--ns-id` deserves a second read before you press enter.

## Verify

- `nginx -t` must say `syntax is ok` / `test is successful`.
  Two warnings are pre-existing on this VM and unrelated to your change:
  `could not build optimal map_hash` and `could not build optimal
  variables_hash`. They appear on a clean config too.
- `supervisorctl signal HUP nginx` prints `nginx: signalled`.
- Re-run `show` and confirm the binding is what you intended.
- End to end: hit the tenant and confirm the request lands in the parallel
  namespace's pod rather than `qa01-mp-npe--webui`.

## Troubleshooting

- **Tenant still shows the old UI.** Confirm the hostname is in `server_name`
  *and* that nginx has been reloaded since the edit. Then confirm the namespace
  actually has a running pod (`qa01-parallel-namespace-deploy`'s `verify`).
- **`Permission denied` reading a config.** Files are `0600 root`; use `sudo`.
- **`grep server_name` returns three hits.** You matched
  `proxy_ssl_server_name`; anchor the pattern.
- **Script says a file already exists.** You are on the first-time path for an
  `--ns-id` that is partly set up. Inspect before deleting anything.
- **Cutover tenant does not route.** Check `/etc/nginx/crane_tenants.map`.
- **`tsh ssh` says the host is offline.** You omitted `--cluster iad0`.

## What this skill will NOT do

- **Build or deploy the namespace** -> `qa01-parallel-namespace-deploy`.
- **Execute a reload, a hand edit, or an `rm` on your behalf without an explicit
  confirmation gate.** The scripts emit commands; a human runs them.
- **Touch production nginx**, or any POP other than qa01/iad0.
- **Add a tenant to `crane_tenants.map`.** That file has other owners; this skill
  only tells you when it is the blocker.
- **ngweb-v2 sidecar routing.** Sidecars route by `x-npe-env` header with label +
  Ingress-path isolation inside a single namespace, with no nginx `server_name`
  binding at all. Use the `sidecar` skill.
